# Recipe Box Decision Log

> **Reference Note:** For full context and comprehensive background on each
> decision, see [comprehensive reference](comprehensive-reference.md).

## Purpose

This log records high-impact decisions and their rationale. It is not a copy of
the product specification or a task list. The canonical behavior remains in
`comprehensive-reference.md`; the discussion folder remains historical context.

| Decision | Rationale |
| -------- | --------- |
| A hosted personal instance starts from the source ZIP: extract it, create a new local repository in GitHub Desktop, copy the source files into it, and publish that repository privately. | A fresh repository has its own commit history and no inherited upstream remote; later upstream changes are not silently incorporated. This matches the intended source-only setup rather than a fork or clone. See [Slice 25](slices/25-go-online.md). |
| Use Publication in the UI. | Book is too narrow for books, magazine issues, and websites. |
| Sites remain standalone primary publications for recipes sourced from websites. | Many recipe websites publish recipes that have no print counterpart; they remain valid recipe origins without being secondary listings for Magazine recipes. |
| Every recipe has a primary publication; Recipe Tin is a reserved collection publication, one per account. | Original recipes have a permanent Library home without being represented by a missing relationship. |
| One ingredient row owns its measurements. | Separate visual ingredient and amount columns must not lose row alignment. |
| Keep volume and weight together when both are known. | A recipe may display `1 cup / 120 g` while retaining both source values. |
| Trusted densities are Settings-only. | Volume-to-weight conversion must be explicit and ingredient-specific. |
| Ingredient density is one explicit volume/weight equivalency per canonical ingredient; recipe amounts are never rewritten when that equivalency changes. | Density is ingredient-specific rather than a universal conversion, and saved recipe measurements remain stable until the recipe owner edits them. |
| Private instruction mentions, temperatures, and durations use independent account colors, initially blue, red, and orange; None removes app-applied color and emphasis while retaining readable body text. Settings provides a **Turn off all emphasis** checkbox below the private-print checkbox: checking sets all categories to None, and unchecking restores the default colors. Private print follows those choices unless its print-emphasis opt-out is selected; DLC 08 adds a separate opt-out for inline instruction photos. Both are print-only. Public output uses fixed defaults and offers transient, text-labeled **No emphasis** and **No instruction photos** controls for screen and print. Authored Markdown formatting is preserved. `F!400` and `C!200` stay visible in the editor; numeric temperatures convert to the account's preferred unit privately and round to the nearest 5 degrees, while public output retains the authored unit and rounds to the nearest 5 degrees. Fahrenheit is the default. Unitless stove labels use `!medium low!`, displayed without delimiters or conversion. Durations are explicitly marked without clock icons. | Explicit editor shorthand preserves authored values while allowing preference-based private display without changing recipe data. Bracketed stove labels mark intentional heat settings without unit conversion. Natural measurement text already conveys meaning, so extra reader symbols add clutter. Per-category and global controls remove app-applied emphasis without hiding or restyling authored Markdown, and public output must not expose account preferences. See [DLC 05](slices/dlc/dlc-05-instruction-authoring-and-references.md) and [DLC 08](slices/dlc/dlc-08-recipe-public-and-print-layout.md). |
| Private Print & Download omits owner-only details by default. A saved Settings preference defaults off, and private Page Settings can override it for the current page; public output never exposes this control or preference. Tags remain excluded from standalone output with either setting. | Owners must explicitly opt in before private-only metadata, notes, pairings, or references are copied into standalone output, while useful recipe content remains printable by default. Tags are not added as a new output field. |
| Instruction photos use stable, unique two-digit per-recipe codes shown on picker thumbnails; typing `+p` opens a caret-anchored overlay pane above or below the step, with no separate picker button. Selection inserts `+photoNN`; typing a valid code directly also references that photo, optionally with `-w<width>` and `-left`, in either order. Existing numeric width suffixes remain readable; new input uses the `w` marker. Readers align the image at the exact inline marker, defaulting right and supporting left alignment. A photo marker authored at the beginning of a new line starts on the next rendered line; inline markers retain wrapping behavior. Later photo-free instructions wrap beside desktop floats; photos are left-aligned blocks on narrow screens. Each photo has at least 1mm of vertical separation. A later photo-bearing instruction is kept clear of existing media. Floats end with the instruction list; default width is 200px. | Stable codes stay meaningful when gallery order changes, while stored UUIDs preserve secure references and import remapping. Inline wrapping keeps a photo beside the exact text it supports while allowing following instructions to use available space. Explicit width notation avoids ambiguity with other modifiers. A later photo-bearing instruction is kept clear of existing media. Photos remain decorative and supplemental; one confirmed removal also removes every reference. See [DLC 05](slices/dlc/dlc-05-instruction-authoring-and-references.md). |
| Recipe-editor density derivation is transient draft state; loaded and manually entered amounts are never silently overwritten. | Owners can distinguish and override an auto-filled amount during editing without adding derivation metadata to the recipe's saved measurements or history. |
| Density-derived amounts use a tinted field and compact calculator icon, with an associated screen-reader status; the amount grows only within its measurement group. | The visible cue stays compact beside the value, assistive technology receives the full status, and longer derived quantities do not collide with the unit picker. |
| Main ingredients are row flags. | Classification stays attached to the actual recipe ingredient. |
| Verdict remains one holistic configurable picklist. | Judgment and practical repeat likelihood are intentionally intertwined. |
| A Magazine publication represents the enduring title; issue, volume, edition/date, and page are recipe-location details. | Recipes from different issues share one Library record while retaining their exact citation. |
| Existing publications are edited in place in Slice 12.5. | A person can correct a Book, Magazine title, or Site without deleting it and risking its recipes, cover, or relationships. |
| Publication type is immutable during Slice 12.5 editing; only the name and current-type details can change. | Converting a Book, Magazine, or Site can invalidate or reinterpret recipe page, citation, and URL data, so metadata edits must preserve linked recipe meaning. |
| Public RPCs use PostgREST status codes for expected concurrency conflicts; use `PT409` for HTTP 409 rather than raising SQLSTATE `40001`. | PostgREST 14 treats `40001` as a transient serialization failure and retries the transaction, which can amplify one conflict into repeated database work, logs, and CPU usage. Application handlers map `PT409` to the existing conflict experience. See [Supabase's retry guidance](https://supabase.com/docs/guides/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b). |
| Publication detail keeps the cover static; Edit opens a pane with the cover manager and the standard Name field side by side. | The cover remains visible without a second edit trigger on the detail page, while its pencil stays available in the dedicated edit workflow. |
| The publication editor uses its close control or Escape to discard; Delete replaces Cancel, remains left of Save, and both actions have equal widths. | Closing discards metadata drafts without implying a save; deletion stays distinct and opens its own confirmation, while balanced action widths improve scanability. |
| Publication detail places Edit at the left of the action row and Add Recipe at the right. | Keep editing distinct from creation while making both actions available in one compact, predictable row. |
| On mobile publication detail, Sort, direction, and View stay connected; List columns and the transfer, Edit, and Add actions remain separate and evenly spaced. List columns uses Edit's outlined treatment. | Preserve the compact explorer group while keeping settings and page actions visually distinct and preventing toolbar overflow. |
| Recipe photos are decorative, have no descriptions or captions, and render with empty alternative text. | Recipe photos visually complement the recipe and should not add redundant screen-reader content or imply required descriptive metadata. |
| Recipe photos and publication covers use reversible, per-asset framing; no saved crop means Fit/contain, and explicit framing is applied consistently across display surfaces. The editor offers an orientation-aware ratio Picklist without a selection checkmark, touch pinch and drag, desktop wheel zoom, icon-only 90-degree rotation without a numeric degree readout, keyboard-operable controls, Reset, Cancel, and Apply. At narrow mobile widths, the controls share one compact row when space permits. Recipe Apply saves immediately; cover Apply stages until Submit. The existing single-image viewer shows the saved frame without gallery navigation. Saving creates versioned official display files and retains the normalized source files for further edits and reset. Bundle v7 preserves all distinct image variants; versions 1 through 6 remain compatible. | This supersedes the earlier metadata-only storage decision: a generated display image removes per-render crop math while retaining reversibility. An explicit frame avoids automatic cropping without changing the safe whole-image default. |
| A saved media crop keeps its aspect ratio in every display; fixed square thumbnail viewports contain and may letterbox it rather than stretch it. | Stretching a saved crop changes the composition the owner chose. Containing it within square thumbnails preserves that composition without distortion. |
| Publication recipe lists use the Recipe Explorer's filters, sorting, and List/Grid views, scoped to that publication in Slice 17; Slice 18 restores their last-used state without losing the scope. | The same recipes should be discoverable consistently from the Recipe Explorer and their publication without losing the publication context. |

Existing full-text search and straightforward filters support one-off discovery; query and saved-view lifecycle complexity is not justified without demonstrated repeated use. Column layout preferences are useful across Find, Library, and publication recipe lists, so they persist per account and exact explorer context. |

Direct manipulation fits the table; this is an explicit accessibility trade-off, while all other explorer controls remain keyboard-operable. |

Existing Verdict values, including “Favorite,” remain unchanged and do not seed Heart. Score clears when State changes away from Tried; Star and Heart apply in any State. Detail markers are immediate, version-checked stamp toggles; Find and publication recipe lists offer emoji-labeled filters that combine with AND. Active custom stamp indicators appear in private List/Grid views, with the marker columns on by default and independently hideable. | A numeric score, a note-worthy marker, and a love/repeat marker describe different things. Keeping Verdict preserves existing meaning; not inferring Heart avoids changing user intent. Private owner-only storage and explicit score values keep personal reactions out of public output and avoid color-only communication. See the [DLC 10 brief](slices/dlc/dlc-10-ratings-and-favorites.md). |
| Explorer state is an account-scoped, last-successful-value preference with no audit, version-conflict, Trash, or purge lifecycle. | Explorer controls can change frequently and do not alter recipe or publication data. | The all-recipes finder is separate from the Recipe Tin collection. | The Tin remains a distinct permanent collection, while people still need one place to find recipes across all publications. |
| Magazine issue citations remain free text and may coexist with the recipe's online URL. | Magazines vary their citation styles, and the citation and URL are independent details. |

| Recipe detail displays the actual online URL as clickable text on desktop and `View online` on mobile. | The full URL is useful on wide screens, while the short mobile link preserves space. |
| In-app References link to recipes only; Publications remain citation text and are not selectable targets. Existing Publication-reference text remains static for data preservation. |
| A selected Pairs With recipe uses a normalized `#slug` token in edit mode; saved and view-mode text remains the readable recipe name. | This mirrors ingredient-link shorthand while preserving readable relationship text and the existing linked-ID contract. |

| Public URLs remain stable when privacy changes. | A Private toggle changes access, not identity or the shared link. |
