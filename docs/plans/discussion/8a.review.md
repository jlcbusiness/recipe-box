The plans are a solid product spec with a sensible vertical-slice roadmap. They aren't yet a plan you can start slice 1 from. A handful of cross-cutting decisions are expensive to retrofit, and several documents contradict each other.

## Works well

- The deferral discipline is good. The roadmap requires a slice brief, re-verification of current framework APIs, and a completion rule for each slice.
- `data-model.md` states relationship rules without pretending to be a schema.
- Deferred features are cleanly listed, and the discussion history explains why each decision was made.

## Settle before slice 1 or 2

These touch every later slice, so deferring them to "the correct slice" is risky.

1. **Source of truth.**
   - `comprehensive-reference.md` calls itself "definitive".
   - `decision-log.md` says `first-draft-spec.md` is canonical.
   - The reference already contains content the spec lacks, such as offline caching and the density re-trigger rule.
   - Pick one authority and mark the others as derived.
2. **Roadmap coverage gaps.** Several features are assigned to no slice:
   - Recipe metadata: state/verdict/enthusiasm, times, servings, equipment and notes. Slice 5 owns picklists, but slice 2 recipes need them with seed values.
   - PWA, service worker and offline caching (§14).
   - Cook mode, wake lock and ingredient check-off.
   - User preferences: mention styling and the default ingredient view.
   - Slice 2 builds ingredient rows with no measurements. Design the measurement schema (ranges, dual volume/weight) in slice 2 so slice 4 isn't a migration.
3. **History mechanism.** Slice 7 owns history, but it must capture changes from every write path built in slices 2–6. Decide up front between database triggers and app-layer logging, and wire it into slice 2.
4. **Instruction editor.** This is the riskiest technical choice.
   - It needs mention nodes, `#` autocomplete, and a plain-text projection for full-text search.
   - Instructions are "rich text" while Notes are "markdown", which is inconsistent.
   - `#` is awkward on mobile keyboards, so a toolbar trigger is needed.
   - Run a spike before slice 2.
5. **Engineering baseline.** There is no plan for:
   - Supabase migrations and CLI workflow.
   - Separate dev and prod projects.
   - Test tooling and CI, including accessibility checks.
   - An accessible component library, which matters because accessibility is not deferred and the ingredient grid and comboboxes are heavy to build by hand.
   - Free-tier limits such as project pausing and storage caps (verify current plan terms).
6. **Security and operations.**
   - Is signup open or invite-only?
   - Public routes need rate limiting.
   - Check how Google sign-in links to an unverified password account with the same email.
   - Define a field allow-list for public views. Notes, verdict, reason and state are personal and shouldn't be assumed public.
   - Plan for multi-device edit conflicts (phone and desktop), for example optimistic concurrency.

## Contradictions and ambiguities to fix in the docs

- **Standard view.** The docs describe it as three columns (ingredient, amount, instructions). They also describe the row order as amount, ingredient, preparation. These are different layouts.
- **Unit-display control.** It isn't clear whether it is per row or global.
- **Rows with both volume and weight.** The "by size" sort doesn't say which group they belong to.
- **Count units.** "cucumber" is listed as a count unit. Decide whether a count with no unit is allowed.
- **Deletion vocabulary.** The docs use archive, trash and delete interchangeably. The 30-day retention and the purge mechanism are never decided.
- **State changes.** If State changes from Tried to Want to try, are the hidden verdict, enthusiasm and occasion values cleared or kept?
- **Ingredient management.** Settings has no rename, merge or delete for canonical ingredients, yet `#` create-new makes duplicates easy. Row deletion with existing mentions is also unspecified.
- **Dual magazine and site listing.** The mechanics are unclear: whether it's a secondary-publication relation and whether the site is auto-matched by URL. It also overlaps with in-app References.
- **Recipe photos.** Photos appear in the media model and export, but the recipe card has no photo UI.
- **Density example.** `1 cup = 254 g` for all-purpose flour is wrong, since it's about 120 g. Reference §8.2 also lists 120 g for cake flour. Fix it before it becomes a test fixture.
- **Decision log.** It omits several real decisions: version restore dropped, app-managed email verification, ingredient-first as a viewer preference, and signed-URL image delivery.
- **Dark mode.** The reference mentions light and dark themes, but v1 scope doesn't say whether dark mode is included.
