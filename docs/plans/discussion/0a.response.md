There’s no implementation to preserve, so the decision is genuinely open. The core constraint is not recipe storage; it’s a relational personal database with a deliberate work-item-style desktop interface and a separately designed, touch-first mobile experience.

**Short Answer**

No existing product cleanly matches this. Recipe apps handle cooking well but have weak data modeling and queries; database/work-management tools handle relations and queries well but make recipes feel like generic records. A custom web app is justified here.

Closest “try before building” options:

- **Coda**: flexible relations, formulas, and views; still feels like a document/database.
- **Airtable / SmartSuite**: strong filtering, linked records, multi-selects; detail views remain pane-oriented.
- **Baserow / NocoDB**: relational and self-hostable, but you would still need a custom front end for the experience you want.
- **Glide / Softr / AppSheet**: can produce a useful mobile-facing layer, but measurement conversion, query-builder flexibility, source deletion choices, and the desired desktop UI will become awkward quickly.
- **Paprika / AnyList / Recipe Keeper**: good recipe tools, poor substitutes for your cross-linked database and Azure-DevOps-style querying.

I would not bend Azure DevOps, Jira, Notion, or Fibery into this. Their data models may get close, but their interaction model is the part you dislike.

**Recommended Build**

Start with a web application, designed as two intentional experiences:

- Desktop: dense work-item details, saved queries, column configuration, keyboard-friendly editing, source library grid/details/preview modes.
- Mobile: touch-first recipe reading, scaling, grocery/cooking use, quick capture, and a compact editor. It should share data and rules with desktop, not duplicate the desktop layout.
- Make it a **PWA** first. It is globally available, installable, and avoids building two clients prematurely. Add a native Expo app only when you need native-only capabilities such as excellent offline capture, barcode scanning, camera import, or notifications.

Technical stack:

- **TypeScript** throughout.
- **Next.js + React** for the web app, deployed to Vercel.
- **Supabase Postgres** for relational data, authentication, row-level security, full-text search, and image storage.
- **Drizzle ORM** or Supabase’s generated TypeScript types plus SQL migrations; I would favor explicit migrations and database constraints over a loose no-code schema.
- **Expo / React Native** later, if the PWA proves insufficient. It can share TypeScript types, validation, unit logic, and API code with the web app.

**Data Model**

Use ordinary relational tables, not one giant flexible “fields” table:

- `recipes`
- `references` or `publications` for books, magazines, sites, and individual web pages
- `recipe_references` for a recipe’s primary reference and optional additional references
- `ingredients` and `recipe_ingredients`
- `equipment` for what you called tools; “Equipment” is clear and pleasantly non-fussy
- `recipe_steps`
- `recipe_relationships` for “pairs with”
- `tags`, plus join tables for recipes and references
- curated option tables for food types, meal types, cuisines, verdicts, enthusiasm, and so on

For the name currently called “source,” I’d use **Reference** in the data model and perhaps **From** in the recipe UI. A book, magazine, website, or page is all a reference to where the recipe came from.

Treat tags and picklists differently:

- **Picklists** are curated fields with consistent meanings, suitable for filters and reporting.
- **Tags** are lightweight, ad hoc labels.
- Settings can merge a picklist value by reassigning all related records before deleting it.

**Important Design Decisions**

A recipe ingredient and its amount must be one ordered record, even if the desktop card displays them in separate columns. Separate lists would eventually lose their alignment.

Unit conversion needs one hard boundary: conversions within the same dimension are reliable, such as cups to teaspoons or grams to kilograms. Volume-to-weight conversion requires an ingredient-specific density, so it should only appear when that ingredient has a trusted density configured. Never silently pretend that one cup equals a universal weight.

Store each recipe as a **base batch** with its original yield and servings. Scaling then has a clear meaning: $2\times$, $1/2$, or a target serving count. “Recipe as entered is always 1” works well for a batch multiplier, but it should coexist with “serves 6.”

Total time should not always be calculated by addition because chilling, resting, and baking can overlap. Keep optional timing fields and allow either a manually entered total or a clearly labeled calculated estimate.

**Contradictions To Resolve**

- Is cuisine single-select, multi-select, or hierarchical? “American” and “Italian” fit a cuisine taxonomy; a dish can plausibly have more than one.
- “Food type” and “recipe type” seem to mean the same thing. Use one field unless you can name the distinction.
- A recipe currently has one source title, but recipes may be adapted from several places. Define a primary reference plus optional additional references.
- A website may be a publication, while a specific URL is the recipe location. Model those as separate concepts.
- Define whether a deleted recipe/reference is permanently removed, archived, or restorable. I strongly recommend an archive/trash period.
- “Chill/freeze/marinade” should be distinct time categories, not one shared field, because they are useful query dimensions.
- State, verdict, enthusiasm, situation, and rejection reason should have explicit conditional rules. For example, `tried` enables verdict; `Want to try` enables enthusiasm; `will not try` enables reason.

**The Query System**

This deserves first-class product work, not a filter drawer added at the end. Support:

- Typed fields and operators: equals, one-of, contains-any/all, is blank, numeric/date comparisons, text contains.
- Nested AND/OR groups.
- Sorts, selected columns, grouping, saved/shared views, and an explainable filter summary.
- Full-text search across title, notes, ingredients, steps, author, and reference.
- A simple mode first, with an advanced mode for Azure DevOps-style compound queries.

Do not make every property infinitely configurable. Keep structural facts such as ingredients, steps, quantities, source links, and statuses strongly modeled; allow configurable values inside their appropriate taxonomies.

**Visual Direction**

Use Azure DevOps as inspiration for information density and query ergonomics, not its whole aesthetic. On desktop, the recipe should read like a well-organized work item: strong title, compact metadata grid, then the three-column cooking body. The source library can use Explorer-style grid/details modes and a preview pane.

On mobile, the recipe should be a cooking document first: title, scaling, ingredients with check-off states, and steps with generous touch targets. Metadata belongs behind a compact section or sheet rather than competing with the recipe.

The permanent unparented **Recipe Tin** is a strong bit of product identity. Give that one special source a tin image and paper-card treatment, while keeping normal recipe cards restrained and readable.

**Missing But Worth Planning**

- Import paths: URL capture, pasted text, manual entry, photo/OCR, and recipe-file import.
- Attribution and copyright handling for copied instructions/images.
- Ingredient aliases and normalization: `bell pepper` vs. `capsicum`, plural forms, brand names.
- Dietary/allergen fields and substitutions.
- Favorites, recently cooked, cook history, ratings over time, and notes by cooking attempt.
- Print/cook mode.
- Backups/export in a portable format.
- Authentication, private-by-default sharing, and future household collaboration.
- Image storage, image rights, and source-cover scanning.
- Accessibility: keyboard-first desktop operation, contrast, screen-reader labels, and a no-drag workflow.

A sensible first release is recipes, references, customizable picklists/tags, relationships, scaling with same-dimension conversions, search/filter/sort, saved views, and the Recipe Tin. Library view variants, OCR/import, sophisticated query nesting, and a native app can follow once the core data is real.
