Yes. The new decisions are coherent. A few details need to be nailed down, but they are now implementation details rather than product-model conflicts.

**Ingredient Density**

Make this a formal Settings-only record attached to an ingredient:

- Enter one volume and one weight value, such as `1 cup = 254 g`.
- Store it internally as a normalized density, while preserving the human-friendly expression shown in Settings.
- When either quantity field is empty on a recipe row, entering or leaving the other field auto-fills it from the trusted density.
- A density-derived value gets a subtle tinted background **and** an accessible “Derived from ingredient density” label/icon; color alone cannot carry the meaning.
- Editing a derived value makes it manual and removes that status.
- Clearing a manual side and leaving the field re-applies the density.

For the first version, allow one trusted density per ingredient. Some ingredients later need variants, such as sifted vs. packed flour, but a single explicit value is a good, comprehensible starting point.

**Instruction Mentions**

`#` autocomplete is a very good fit. Use structured inline ingredient references under the hood, even though the editor accepts `#all-purpose-flour`.

That gives you:

- A typeahead immediately after `#`.
- Narrowing suggestions as more text is entered.
- An explicit “keep as text” option.
- A rendered instruction that displays `all-purpose flour`, not the hyphenated editor token.
- Reliable ingredient ordering and rename support without breaking old instructions.

A mention should count toward “appears in instructions” only when it is an actual selected ingredient reference, not plain text typed after `#`.

**Verdict**

Agreed: do not split cadence from verdict. Your verdict is intentionally a holistic judgment about pleasure, practicality, novelty, and when you imagine making the thing again. Keep it as one customizable conditional picklist.

`Specific occasion` can reveal an occasion text field. `Occasionally` remains its own verdict meaning “worth returning to, but not often.” That captures the useful ambiguity rather than flattening it.

**Publications**

The magazine plan requires two publication associations:

- The individual magazine issue is a Publication, with required free-text issue/edition/date and optional recipe URL.
- The website is a separate Site Publication.
- When the recipe has both, it is listed under both publications, while the magazine issue remains the recipe’s originating publication.

The library can filter by book, magazine, or site. A book gets optional edition, ISBN, and retailer/reference URL. The top of the recipe card can show its originating publication, while the References section shows supplemental sources.

**Change History**

This is feasible and worthwhile. Record a history entry on save, not on every keystroke:

- Created, edited, archived/deleted, restored.
- Changed fields with before/after values.
- Ingredient, instruction, tag, relationship, publication, and reference changes.
- Timestamp and account that made the change.

Keep history inside the application and exclude it from the recovery export, as requested. The export recreates the current state; it does not recreate its diary. I recommend including a “restore this version” capability from the beginning, since history without recovery is mostly a forensic convenience.

**Accounts**

A per-person “skip verification” choice cannot use Supabase’s built-in confirmation alone, because that setting is project-wide. The clean implementation is:

- Password accounts are immediately usable.
- Sign-up offers “Verify my recovery email” by default and “Skip email verification” as an explicit alternative.
- Checking skip opens the warning you described: no confirmation means a typo can prevent password recovery.
- Verification is an app-managed email link, while password-reset links still go to the entered email address.
- Google sign-in remains an alternative, not a requirement.

That preserves easy signup while making the recovery consequence clear.

**Two Final Clarifications**

1. On a public recipe page, do you want unit-conversion controls as well as serving scaling and print? You specified that scaling and print are the only clickable functions; a unit selector would be another interactive control. My recommendation is: public pages show the recipe’s stored units, with scaling and print only.

2. Should a public recipe URL remain unchanged after the recipe becomes private, or should it return a generic “not available” page? The latter is safer and avoids revealing that a private recipe exists.
