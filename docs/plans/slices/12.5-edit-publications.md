# Slice 12.5: Edit Publications

This brief defines in-place editing for an existing Book, Magazine title, or
Site. Editing changes the existing record; it does not replace it or disturb
its recipes, relationships, or cover.

## Outcome

A signed-in owner can update the name and type-specific details of an active
publication from its detail page. The edit is explicit, validated, owner-scoped,
and version-checked. Saving preserves the publication ID, its recipes and recipe
locations, its relationships, and its cover. Closing with X or Escape discards
unsaved changes.

## Decisions

- Publication type is immutable after creation in this slice. The editor shows
the current type and only that type's fields. Conversion could invalidate or
reinterpret recipe page, citation, and URL data; conversion is not silently
coupled to metadata editing.
- Common field: Name is required and trimmed.
- Book fields: Author, Edition, ISBN, and Retailer URL are optional. A non-empty
ISBN must be a valid ISBN-10 or ISBN-13 and is stored without separators. A
non-empty URL must be HTTP(S); a scheme-less host is normalized to HTTPS.
- Magazine fields: only the Magazine title/Name is editable. Its case- and
trim-insensitive uniqueness within the account is enforced by the existing
unique index. Existing recipes retain their own issue and page citation.
- Site fields: Site URL is required and must be HTTP(S); a scheme-less host is
normalized to HTTPS.
- Empty optional text and URLs are stored as null. Fields not belonging to the
publication's type remain null.
- Every successful explicit save increments the publication version and records
one append-only `publication.updated` history event with before/after snapshots.
- A stale version, trashed/missing record, invalid type-specific data, or
cross-account ID is rejected without changing the publication or its history.
The edit UI reports conflicts and keeps the form open; the owner can close and
reopen it to load current data.
- The detail page shows a static cover. In the edit pane, the cover image and
  pencil open the existing cover manager beside the standard Name field. The
  spacing accounts for the pencil's overhang. Cover changes remain a separate
  interaction bound to the same publication ID, not part of the metadata save.
- No tags, publication recipe explorer, import/export behavior, or publication
type conversion is added in this slice.

## Data and mutation contract

- Add a forward migration; do not rewrite prior migrations or introduce a new
table. Keep the current RLS read boundary and do not grant direct authenticated
`UPDATE` access to `publications`.
- Add an authenticated-only `update_publication` RPC. Derive ownership from
`auth.uid()`; accept the publication ID, expected version, name, and
current-type fields, but no account ID or replacement type.
- Lock the active owned publication row, check the expected version, validate
its existing type and submitted fields, and update atomically. The RPC returns
the new ID and version. Use an empty `search_path`, schema-qualify relations,
and revoke execution from `public` and `anon`.
- Record update history through a database trigger. Permit the new event type in
the history constraint. Preserve the existing create and lifecycle event
behavior; lifecycle-only writes must not create a second update event.
- The server action independently authenticates and validates `FormData`,
normalizes ISBN/URLs using the existing publication validation utilities, calls
the RPC, maps stale/duplicate/validation failures to useful form errors, and
revalidates the Library and detail route after success.

## UI and interaction

- Add an Edit icon action to the left side of the publication detail action
  row. Place the compact Add Recipe link at the right side of that row. The Edit
  action has the accessible name `Edit publication`, a matching `title`, visible
  focus, a mobile hit area of at least 48 by 48 px, a page-paper background, and
  the same leaf-green border color as Add Recipe. Show the cover image without
  an edit trigger on the detail page.
- Open a labeled native modal dialog titled `Edit publication`; focus the Name
  field when opened. Keep the current type visible and fixed, and show only
  applicable fields with visible labels. Place the standard Name field beside
  the cover control and preserve the visible spacing beyond its pencil
  overhang. Reuse the established publication form layout and ISBN interaction.
- Save and Delete are visible text actions. Delete opens the existing
  publication deletion confirmation. Keep Delete left-aligned and Save
  right-aligned at equal widths on desktop and mobile; mobile buttons use equal
  padding on all sides and retain at least 48 px height. Disable Save while
  pending. The top-right close control and Escape discard the draft and close
  the dialog; failed validation or a version conflict keeps it open and
  announces the error with `role="alert"`.
- On success, close the dialog, show the updated detail values, and retain the
existing cover and recipe listing. Keep the layout usable at desktop and mobile
widths without horizontal page overflow.

## Test-first acceptance

Write focused failing tests before production implementation:

- Unit validation covers trimmed names, ISBN-10/13 validity, HTTP(S) URL
normalization, rejection of other schemes, optional empty fields, and required
Site URLs.
- Database/API coverage proves owner-only update, rejection of anonymous and
foreign-owner writes, stale-version and trashed-record rejection, duplicate
Magazine-title rejection, no mutation/history on rejection, one version bump
and one `publication.updated` snapshot on success, and correct clearing of
inapplicable type-specific fields.
- End-to-end coverage edits a Book, Magazine, and Site; verifies the saved
  values; confirms closing without saving leaves stored values unchanged;
  verifies invalid ISBN and URL feedback; and proves an edit does not change
  the publication ID, associated recipe locations, relationship rows, or cover
  asset association.
- A deterministic stale-version test confirms the conflict is perceivable and
no stale values are persisted. A second account cannot edit the record.
- Chromium and Fold 6 browser coverage verifies dialog keyboard operation,
  focus placement/restoration, Escape cancellation, visible labels, touch target
  size, cover/Name layout, equal-width Delete and Save actions with their
  responsive alignment, no horizontal overflow, and axe results.

## Verification

Use focused unit and publication E2E/accessibility tests first. Then run the
relevant local migration lint, `npm run typecheck`, `npm run lint`, and the
production build. Reuse local data when useful; a reset is allowed when a clean
baseline is worth the reset and reload effort. Follow the README procedure and
reload the synthetic fixture. Never reset linked or hosted Supabase.

## Completion criteria

- All acceptance tests pass against local Supabase on Chromium and Fold 6.
- Successful edits preserve recipe/location, relationship, and cover identity;
failed or stale edits make no partial change.
- History contains exactly one edit event per successful save, with immutable
ownership and no direct table-write permission added.
- Update the comprehensive reference, visual guide, decision log, and roadmap
to describe only behavior that passed the acceptance tests.
